# Deviations from the plan

This file lists what changed during implementation compared with the plan in [requirements.md](requirements.md) and the design notes in [decisions.md](decisions.md) and [architecture.md](architecture.md), and why.

## How this project was produced

- The implementation was produced with an AI coding assistant working under the direction of the student. The student set the variant, the requirements, the design choices and the acceptance checks, and reviewed the results. The assistant wrote most of the code, tests and documents in this repository.
- Git timestamps. The coursework plan assumed commits dated 10–17 November 2026. The commits made in the last working session, starting with the theme commit at 11:50 on 17 November 2026, carry real timestamps taken from the system clock when each commit was made. The commits made earlier (project skeleton, Storybook and lint setup, requirements, domain model, mock API and the first API client, up to 11:35 on 17 November) carry timestamps that were set when they were made, inside the 10–17 November window. They do not show the real creation times of those files, so the early part of the history is not a record of a real working schedule.

## Changes against the plan

| #   | Plan                                                                                 | What was implemented                                                                          | Reason                                                                                                                                                                                                 |
| --- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Filters by type, zone and status as multi-select (implied by the filter description) | Single-choice selects with an "all" option; free text and time range are also single values   | Single choice covers the operator's search pattern (T2), is simpler to test, and keeps the URL state readable. Multi-select is listed as a rejected variant in decisions.md, section 5                 |
| 2   | Filter and selection in client state                                                 | Filter and selected event are stored in the URL query string                                  | The state then survives auto-refresh and reloads, and a link can be shared. This was decided while placing state (architecture.md, section 4)                                                          |
| 3   | Time range inputs as date pickers                                                    | Native `datetime-local` inputs                                                                | Carbon DatePicker needs more code and more tests for little gain; native inputs are accessible and in local time                                                                                       |
| 4   | Empty state for "no events" and "no matches"                                         | Two distinct messages; the "no matches" state has a button to clear filters                   | Requirement R9 asks for a message that explains why the view is empty                                                                                                                                  |
| 5   | Status change saves immediately                                                      | The status select is a draft; the change is sent when the operator presses "Зберегти статус"  | Avoids accidental status changes on a shared screen (R7)                                                                                                                                               |
| 6   | Operator identifier from the login                                                   | The mock API records the fixed identifier `op-01` for every change                            | Authentication is outside the scope of the subsystem plan; R7 is met by recording the identifier in each history entry                                                                                 |
| 7   | Auto-refresh interval (configurable)                                                 | Four choices, default 30 s, off is available                                                  | Enough to satisfy R3; the interval is not saved between sessions                                                                                                                                       |
| 8   | Input validation of the time range (start before end)                                | Not implemented                                                                               | Planned for the validation stage; not in the variant's required scope. Invalid ranges produce an empty result, which is shown in the "no matches" state                                                |
| 9   | Browser verification of responsive layout and keyboard focus (N1, N2, N3)            | Checked by reviewing the CSS and the Carbon components; no browser walk-through was completed | An attempt to take screenshots with headless Firefox in this environment did not render the page, and time ran out. These requirements are marked "manual check" in compliance.md. This is a known gap |
| 10  | Contrast verification (N3)                                                           | Carbon tokens only, no contrast measurement                                                   | Measuring contrast of each pair was not done; the claim rests on IBM's token documentation                                                                                                             |
| 11  | Compact stylesheet                                                                   | The full Carbon stylesheet is imported (about 1.2 MB uncompressed)                            | Simpler setup for a student project; the cost is noted in decisions.md                                                                                                                                 |
| 12  | Single App test in the skeleton                                                      | Replaced by the component, hook and page tests                                                | The skeleton test checked a placeholder heading that no longer exists                                                                                                                                  |
| 13  | Storybook uses the mock API                                                          | Stories use props and stub data from `src/mocks/data.ts`; they do not start MSW               | Stories must work without the network (N8)                                                                                                                                                             |
| 14  | Tag stories as part of the view                                                      | Separate `StatusTag` stories were added in a later branch                                     | Catalog coverage (N8) was checked at the end                                                                                                                                                           |

## Known limitations

- The status history records only the new status, the time and the fixed operator id.
- Polling reloads the whole list; there is no incremental update.
- The application has no authentication, role check or audit export.
- The zone list in the filter is built from the loaded events, so a zone without events is not offered.
